# Ключи задач и история в комментариях

> Исходный дизайн до реализации. Что поставлено — в `DESIGN.md` §5 «L2 — comments»; при
> расхождении верен `DESIGN.md`.

## Задача

Пользователь (29.10): в коде много комментариев с номерами задач; код должен объяснять себя сам.
Сейчас `is_directive` даёт иммунитет любому комментарию с `[A-Z]{2,}-\d+` или `#\d+`, поэтому
комментарий с ключом не попадает ни в один детектор. В jira-team-analytics ключи стоят в 1454 из
2476 файлов (≈4 тыс. вхождений), аудит этого не показывал.

## Решения

**`ticket_ref` — считаемый класс.** Строка комментария, где есть голый ключ трекера:
`[A-Z][A-Z0-9]+-\d+` (Jira, `GH-12`) или `#\d+` после слова-маркера (`issue`, `PR`, `pull`,
`fixes`, `closes`, `see`, `задача`, `тикет`). Голый `#123` без маркера не считается: это и цвет
`#333`, и номер пункта списка.

Не считаются:

- ключ внутри URL: ссылка открывается у любого читателя, голый ключ — только у того, у кого есть
  трекер и контекст задачи. URL по-прежнему даёт иммунитет всему комментарию;
- строка с task-тегом `TODO`/`FIXME`/`XXX`/`HACK`: ключ у TODO — принятая практика, он называет
  работу, которой ещё нет в коде;
- префиксы стандартов и форматов (`UTF-8`, `ISO-8601`, `SHA-256`, `RFC-…`, `PEP-…`, `Q1-2025`
  и т. п.) — встроенный стоп-лист, плюс `ticket_ref_ignore` в `.code-health/config.json` для
  доменных терминов конкретного репозитория (`TIER-2`). Конфиг нужен потому, что стоп-лист
  стандартов никогда не полон, а ложное срабатывание в guard блокирует коммит.

Класс ортогонален остальным: строка может быть и `trivial_doc`, и `ticket_ref`.
`noise_comment_lines` — объединение строк считаемых классов, а не сумма. Единица — физическая
строка с ключом, а не весь блок: в 20-строчном docstring с одним ключом шум — одна строка.

Точность считаемого класса должна быть ≥ 0.85 (`references/quality-policy.md`). Мерить на живом
коде: выборка срабатываний из jira-team-analytics и ещё одного репозитория, каждое прочитано.

**`history_note` — только `evidence`.** Строка, рассказывающая историю кода вместо его смысла:
`раньше`, `теперь`, `ранее`, `переехал`/`перенесли`, `до/после правки|фикса|рефакторинга|миграции`;
`previously`, `formerly`, `used to` (не «is used to»), `was moved/extracted/rewritten`,
`moved out of/from`, `the old code`, `before/after/since the … fix|refactor|migration`.
`было`, `was`, `now`, `больше не`, `no longer` не входят: в выборке это в основном описание
поведения («сдвигать было нечего», «no longer than X»). Точность ниже порога, поэтому класс не
суммируется — как `short_inline`.

**Плотность — только `evidence`.** `comment_lines`, `lines` (непустые), `ratio`. Метрикой не
становится: дизайн `comment_noise` отверг плотность (Arafati & Riehle 2009 и др.). Нужна, чтобы
отчёт показывал файлы, где комментариев больше, чем кода.

**Итоги слоя.** `layers.comments.totals`: суммы по файлам для `noise_comment_lines`, `ticket_ref`,
`history_note`, `comment_lines`, `lines` и число файлов с `ticket_ref`. Строка «Comment noise»
отчёта аудита читает их.

**guard.** Новая файловая метрика `ticket_refs` в ратчете: `warn = 1`, вне `thresholds` (как
`comment_noise`, порог не настраивается). Новый файл с ключом в комментарии не проходит; старый —
не может прибавить ключей. Базовая линия без поля `ticket_refs` для файла — метрика для него не
проверяется до `update-baseline`. guard не импортирует `code_health`, поэтому извлечение
комментариев и детектор продублированы и закреплены тестом согласия.

**fix.** Группа `comment_noise` может чистить оба класса: из строки `ticket_ref` убрать ключ и
оставить смысл; `history_note` переписать в строку «почему», историю оставить git. Строки
`ticket_ref` входят в защищённое множество правила 6; `history_note` — нет (как `short_inline`).
