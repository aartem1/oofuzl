# Изменения

## 0.7.0

Аудит без работающего Sonar больше не запускается.

- Перед любыми замерами `scripts/sonar_ready.py` поднимает Sonar: запускает Docker (на macOS — `open -a Docker`, ждёт до 3 минут), берёт свежий образ SonarQube Community Build, переиспользует, запускает или создаёт контейнер на постоянных томах, ждёт готовности сервера, находит или выпускает токен и скачивает свежий сканер. Что-то не получилось — аудит останавливается, называет причину и одну команду для исправления. Docker плагин не устанавливает.
- SonarQube плагина работает на PostgreSQL (`code-health-sonarqube` и `code-health-sonar-db`): встроенная база H2 обновление не поддерживает. Перед обновлением сервера база сохраняется копией, миграция запускается, когда сервер её просит; если миграция не прошла, копия и прежняя версия возвращаются. Старый контейнер на встроенной базе останавливается, но не удаляется, его тома остаются.
- Убраны аудит без Sonar, строки «не измерено» для Sonar и откат на встроенный профиль при нехватке прав.
- Покрытие подаётся в Sonar, если в репозитории есть команда тестов с покрытием; отчёт пишется вне репозитория.
- Рейтинги объясняются: `scripts/sonar_ratings.py` называет задачи, которые задают букву, и что нужно для следующей. Аудит решает по каждой задаче — настоящая проблема, ложное срабатывание или настройка сканера — и ставит группы, поднимающие рейтинг, первыми с ожидаемой буквой. `fix` после правки такой группы заново прогоняет анализ и показывает рейтинг до и после.
- `measure.py --update-tools` ставит последние стабильные версии lizard, jscpd, madge и vulture; версии попадают в отчёт, журнал и историю, и сравнение с прошлым аудитом говорит, если изменились инструменты. Не обновилось — остаётся установленная версия.
- Версии сервера SonarQube и сканера тоже попадают в историю (`--tool`). Строка истории дописывается только после успешного анализа Sonar (`--compare-history`, затем `--record-history`), так что остановленный аудит не становится точкой сравнения.
- Чужой SonarQube (`SONAR_HOST_URL` не на localhost) только проверяется: Docker, обновление, пароль администратора и выпуск токена касаются лишь своего локального сервера.
- `guard` по-прежнему пишет эталон закреплённым lizard 1.23.0, теперь отдельной копией, чтобы не откатывать общий lizard; `check` и `update-baseline` тоже берут эту копию.
- Предупреждение Python (`SyntaxWarning`) в выводе vulture больше не помечает слой мёртвого кода как частичный.

## 0.6.0

Исправления по ревью 13.11.

Аудит (`measure.py`):

- Вложенность считается только для Python: у lizard счётчик вложенности переходил из файла в файл, и TS/JS-функции получали чужую глубину.
- Слой мёртвого кода снова выдаёт находки: vulture 2.16 сообщает о них кодом 3, а плагин считал его сбоем. Версии vulture, jscpd и madge закреплены.
- Разобранный объект в параметрах JS/TS (`({ a, b, c }) =>`) считается одним параметром.
- Одноимённые методы разных классов и вложенные функции различаются по полному имени (`Job.run`, `outer.inner`); идентификатор находки больше не содержит номер строки.
- Функция и вложенная в неё функция не считаются дублем.
- Тесты TSX/JSX, `__tests__`, `.yarn`, `coverage` и `*.min.js` не считаются исходным кодом.
- Точные клоны ищутся только между файлами кода, и `--files` сужает их; временная папка jscpd удаляется.
- Граф импортов JS/TS больше не обрывается на 64 КБ.
- Размер файлов `.vue`, `.svelte`, `.sql`, `.sh` измеряется (только строки и токены).
- `--brief N` — сжатая сводка: статусы слоёв, число находок по видам и N худших каждого вида.
- `--history FILE` — одна строка на аудит, чтобы видеть, как меняется код.

Проверка перед коммитом (`guard.py`):

- Папка `.code-health/` никогда не проверяется: первый коммит после установки больше не падает на самом `guard.py`.
- Коммит, который поднимает потолки через `baseline.json` или `config.json` (поднятый эталон, ослабленный порог, новое исключение, удалённая из записи или пропущенная в новой записи метрика, понижённая схема, удалённый эталон), отклоняется. Хук запускается при каждом коммите (`always_run: true`), иначе коммит, который только удаляет эталон, его не вызывал. Подсказки про `--no-verify` в тексте отказа больше нет.
- `--base REF` — та же проверка на сервере сборки для всех изменений ветки от точки, где она отошла от `REF`. Без общей истории с `REF` проверка завершается с кодом 2, а не проходит молча.
- `update-baseline` не записывает эталон, который поднимает потолки, без `--accept-worse`. Такой эталон человек коммитит сам через `git commit --no-verify`, а проверка `--base` показывает его в пул-реквесте.
- Новые строки, отключающие линтер (`noqa`, `type: ignore`, `eslint-disable`, `@ts-ignore` и подобные), считаются по правилу «не больше, чем было».
- Файл, перенесённый `git mv`, сохраняет эталон старого пути до следующего `update-baseline`, а не только в коммите переноса.
- Сбой lizard выводится предупреждением, а не проходит молча.

Навыки: `fix` напоминает запустить `update-baseline` после улучшения и может работать в git worktree — журнал долга общий для всего репозитория.

Как обновиться в репозитории с установленной проверкой: заново скопировать `scripts/guard.py` в `.code-health/guard.py`, добавить `vue, svelte, sql, shell` в `types_or` хука и строку `always_run: true`, затем запустить `update-baseline`. Старый эталон читается и без этого. Большие файлы `.vue`, `.svelte`, `.sql` и `.sh`, которые уже были в репозитории, и старые `# NOQA` заглавными попадут в эталон как есть: первый `update-baseline` после обновления не считает их поднятыми потолками. Запустите его сразу после замены `guard.py`: до этого коммит, который трогает такой файл, проверяется по старому эталону и может не пройти.
